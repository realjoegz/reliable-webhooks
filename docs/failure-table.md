# Kill table and failure table

Each row names one failure, what the service does about it and the tests that prove it. The build runs `FailureTableCheck` after the integration tests, and it fails unless every test linked from a table in this file ran and passed in the same build.

The [kill table](#kill-table) comes first, then the [failure table](#failure-table), then [how the rows are proven](#how-the-rows-are-proven): how the proofs are made, how long a test has for each step, and where a row claims less than a reader might take from it. [design.md](design.md) has the same rows in sections 3 and 13, with a shorter account of how each is forced. `FailureTableCopiesTest` holds the two copies to each other.

## Kill table

Each row is a SIGKILL of a real replica process, landed at a chosen point.

| # | SIGKILL lands | State left | Recovery | Visible effect | Test |
|---|---|---|---|---|---|
| K1 | In the ingest transaction, before commit | Nothing; Postgres rolls back | Producer retries with the same key | One event, one delivery per endpoint | `IngestKillIT#killedBeforeCommit` |
| K2 | After ingest commit, before the response | Event and deliveries committed | Retry returns the original event id with `Idempotent-Replay: true` | One event | `IngestKillIT#killedAfterCommitBeforeResponse` |
| K3 | After claim commit, inside the load of an ordinary closed-circuit delivery, before any byte is sent | Row leased, attempt consumed, no request | Lease expires, another replica reclaims | Attempt 1 logged `unknown`; subscriber sees one request | `WorkerKillIT#killedAfterClaimBeforeSend` |
| K4 | Mid-request | Row leased; subscriber may have processed | Same as K3 | Up to two requests, same `webhook-id` | `WorkerKillIT#killedMidRequest` |
| K5 | After the subscriber's 2xx, before finalize commits | Row leased; subscriber has processed | Same as K3 | Exactly two requests, same `webhook-id`; one `succeeded` | `WorkerKillIT#killedAfterResponseBeforeCommit` |
| K6 | Mid-request of a probe, holding the probe slot of an open circuit | `next_probe_at` pushed 60 s ahead; probing delivery leased | Slot reopens when that time passes; no stuck state | Next probe 60 s after the gate | `EndpointOutageIT#probeSlotReopensAfterProberKilled` |

- K2 is state-equivalent to a lost response, and no signal can be landed between a commit and the response that follows it. The test sends the request and throws the answer away, reads from the database that the event is committed, kills the replica and sends the request again to another one.
- In K4 the request of the first attempt has arrived when the kill comes, because the receiver holds it. The subscriber therefore sees two requests.
- In K6 the lease is aged past its end before the probe time is. The delivery is due then, the worker of the replica inside the test JVM is running as the second replica, and a canary for another endpoint is delivered while the delivery stays as the kill left it. Once the probe time is aged by the 60 s of the slot, that replica claims the delivery, logs the attempt of the dead one as `unknown` and sends the next probe, which is answered with a 200 and closes the circuit.
- A SIGKILL during graceful drain is K4 or K5.
- **Orphaned statements.** Killing a replica does not cancel the statement its backend is running. That statement may still execute, and an autocommit statement may still commit. Safety relies on the lease token and on every autocommit write being harmless when orphaned, not on the statement having stopped. The autocommit writes are the gate, the release, the bucket charge, the delete of an endpoint, the admin patch, the endpoint patch, the key rotation and the secret rotation. An orphaned gate takes a probe slot for a probe that nobody sends, which is what K6 leaves: the slot is free again 60 s later. An orphaned release gives a delivery back that nobody is sending, which the next claim takes. An orphaned charge takes units for an event that is not stored, which is what a charge leaves whose transaction failed: the limiter errs on the strict side. An orphaned delete deletes the endpoint that the tenant asked to delete. An orphaned admin patch sets what the operator asked for, and an orphaned endpoint patch sets the event types the tenant asked for. Repeating either patch changes nothing. A rotation whose response was lost leaves a key that nobody holds, and the operator repeats the call. A secret rotation whose response was lost leaves a secret that nobody holds, and the repeat of that call ends the 24 h of the secret from before the first. No proof of this table blocks an autocommit write: a kill is landed on a read or inside a transaction.
- **Lost response of a create.** `POST /v1/endpoints` and `POST /admin/tenants` are transactions, so one that outlives its replica does not commit by itself. A response that is lost after the commit leaves the row, and the secret or the key in it was shown to nobody. The repeat of the call creates a second row (limitation 37 of the design).

The kill table has rows K1 to K6, which are all the kills of the design. None of them lands while an endpoint or a tenant is created. That an endpoint is not left without its circuit row, and a tenant not without its bucket row, is tested with those two transactions failing without a kill, in `EndpointApiIT#failedCircuitInsertLeavesNoEndpoint` and `AdminApiIT#failedBucketInsertLeavesNoTenant`.

## How the rows are proven

- Rows 1 to 4, 8, 20 and 26 are proven with replicas that run as processes of their own: the packaged jar in a child JVM, with the configuration that ships and the allowance for the local receiver. A kill is a SIGKILL of such a process and a shutdown is a SIGTERM. The replica inside the test JVM only takes the requests that set those tests up. Its worker does not run, so a delivery of such a test is claimed by a process and by nothing else. Rows 9 and 10 have one test each that kills such a process: `EndpointOutageIT#probeSlotReopensAfterProberKilled` and `#expiredAfterHolderKilledReplaysCleanly`. In these two the worker of the replica inside the test JVM does run, but never while the process does. It fails the delivery five times and is stopped before the process is started, and it is started again once the process is gone: in the first test as the second replica, which sends the next probe, and in the second to deliver the replay.
  - No kill is landed by timing. For rows 2, 3 and 4 the test holds a lock that the next statement of the replica needs, waits until `pg_stat_activity` shows the replica waiting for it, kills the replica and lets go of the lock only when the process is gone. For row 1 and for the two kills of rows 9 and 10 the receiver holds the request. The blocked statement is a read or lies inside a transaction, so the backend that outlives its replica commits nothing. The test waits until that backend has left before it asserts what the kill left behind.
  - A blocked statement fails when the lock timeout of its pool is over, after 2 s in the API and after 5 s in the worker. The test has that long to see the replica waiting. A run that missed the wait would fail and not pass.
  - A held request is cut at the attempt deadline of 15 s. Rows 1, 8 and 20 act while the receiver holds the requests of a replica, and have that long for it: row 1 kills the replica, row 8 stops the container, and row 20 sends the SIGTERM, waits for `poller_stopped` and asks the readiness probe. The two kills of rows 9 and 10 have the same 15 s. A run that took longer would fail and not pass: a request that was cut is recorded as a failed attempt, where row 1 shows no attempt row and rows 8 and 20 show a `success` for each request that was held. Rows 2 and 26 hold a request only while the test takes its lock on the delivery row.
  - In row 8 the receiver holds its eight requests until the container has stopped, and answers them then. Two limits apply. The eight requests have to arrive and the container has to stop inside the 15 s of the attempt deadline. The eight results then have to be recorded before the replicas give the finalize up, 55 s after their claims began, so stopping and starting the container together have to fit into that time. A run that took longer than those 55 s would fail and not pass as well: the deliveries would be claimed again and sent a second time. Every answer to the event that is sent while the database is down, and again until it is back, is a 503, and the answer after that is a 202 for a new event.
  - The database of the tests runs with `fsync` off, and row 8 stops its container, not the machine under it. The row is about a database that restarts. It says nothing about one whose machine went down.
  - Row 8 links three unit tests as well. The restart test does not choose which failure a call meets while the database is away: a session that the server ends, a borrow that finds no connection inside its wait, or a statement whose connection has failed, which the driver reports with a state of class 08. A run does not have to meet the last of them. `DatabaseFailuresTest` shows that a state of class 08 counts as transient, `FinalizeRetryTest` that a finalize is tried again after a failure with such a state, and `ProblemsTest#failedConnectionIsDatabaseBusy` that the API answers one with a 503.
  - In row 20 the readiness probe of the replica answers `OUT_OF_SERVICE` while the four requests are held and the poller has stopped, so the worker drains before the web server stops. That the process ended before a lease ran out is read from the four deliveries: each keeps the end of its lease as its due time, and that time still lies ahead on the database clock when the process is gone.
  - In row 26 the replica is cut off while it is seen waiting in its claim, or in the first statement of its finalize transaction. The first test finds the read that timed out in the output of the replica. After the 15 s of the socket timeout the replica still has to pass over the other connections of its pool, one aliveness test of 1 s each, before a claim gets a connection that was opened after the cut ended. The second test waits until the server has ended the transaction and does not measure how long that took. The limit of 10 s is what `DatabasePoolsIT` reads from a live session of each pool.
- In row 14 the circuit of the healthy endpoint is read while the lookups of its tenant are stuck and its delivery has been given back. It is closed and has counted no failure. The circuit of the stuck endpoint has counted its four.
  - The 2 s of the lookup wait are shown from below, and from above only with room for a slow machine. In `SlowEndpointIsolationIT#slowDnsDoesNotStarveOthers` an attempt whose lookup is stuck is recorded with a duration of 2 s to 7 s, and in `SsrfIT#registrationDnsLookupIsBounded` a registration for the stuck host is refused after 2 s to 10 s. A wait a few seconds longer than 2 s would pass both.
- Rows 13 to 15 and 27 hold requests or lookups open and assert while they are. So does `EndpointOutageIT#recoveryDrainsHeldDeliveries` of row 9, which has a canary delivered while the receiver holds four requests of the endpoint that answers again. A held lookup stays stuck until the test lets go of it. A held request is cut at the attempt deadline of 15 s, so those tests have that long, and a run that took longer would fail and not pass: the replica would by then have sent the requests that the test shows it does not send.
- Row 16 is proven inside one test JVM. The four replicas of `limitIsExactAcrossReplicas` are the replica of the class and three more that the test starts the way the application starts. Each has its own pools, key cache and request permits, and they meet in the database, where the bucket is.
  - A test that counts units gives its tenant a rate of 0, so the bucket holds what the test put into it and nothing refills while the test runs. The bucket row is read after each charge. The size that a body is charged for is the size of the body as it is stored, which the test reads from the event row.
  - `limitIsExactAcrossReplicas` has two parts. The 200 events show that the four replicas have one limit, and leave it to chance whether two charges meet at the bucket row. The second part forces that. The test holds the bucket row of a second tenant, which has 3 units, until `pg_stat_activity` shows two charges of each replica waiting for it. Once it lets go, three of the eight events are accepted and five are refused. A charge that waits is ended by the lock timeout of the `api` pool after 2 s, so the test has that long from the first of the eight charges to the release of the row.
